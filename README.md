### 개선 결과

| 항목 | 전 | 후 |
| :--- | ---: | ---: |
| 공지 상세 API 처리 시간 (평균) | 832ms | 5 ~ 11ms |
| 1초를 넘는 상세 응답 | 4 / 20건 | 0 / 600회 |
| 가장 무거운 게시판의 목록 1페이지 | 2.2MB | 6.7KB |
| 26개 게시판 1페이지 응답 합계 | 3.5MB | 188KB |
| 푸시 발송 대상 게시판 | 5 / 26개 | 26 / 26개 |
| 달구지 시간표 동기화 | 연 365회 | 연 33회 |
| 백엔드 자동 테스트 | 50개 | 141개 |

상세 응답 시간은 네트워크를 제외한 서버 내부 처리 시간이고, 로컬 환경에서 측정했습니다.
목록은 응답 크기 기준이며, 같은 DB 스냅샷에 수정 전후 코드를 각각 실행해 비교했습니다.

### 문제를 푼 과정

**목록 응답이 비대했던 원인을 측정으로 바로잡음**
처음에는 공지 본문이 원인으로 지목됐지만, 본문 평균은 약 340자였습니다. 실제 원인은 과거 공지 일부에 그대로 저장된 base64 이미지(행당 최대 약 130만 자)였습니다.
목록 응답은 앱이 쓰는 필드만 내려주고 본문·이미지·첨부는 지연 로딩하도록 바꿨습니다. 앱 코드 변경 없이 적용했습니다.

**푸시 알림이 가지 않던 구독을 찾아 복구**
DB의 발송 이력을 분석했더니 앱은 26개 게시판 구독을 받는데 서버는 5개 게시판만 발송하고 있었습니다. 2026년 6월 스냅샷 기준 구독 183건 중 66건(36%)이 알림을 받을 수 없는 상태였습니다. 발송 대상을 전체 게시판으로 넓혔습니다.

**AI 코드 리뷰 결과를 그대로 믿지 않고 검증**
외부 AI 리뷰가 Critical로 분류한 6건을 실제 코드, DB, API 응답과 대조했습니다. 그대로 Critical로 남은 것은 1건이었고, 나머지는 재현되지 않거나 원인이 달랐습니다. 잘못된 진단을 기반으로 한 수정을 피할 수 있었습니다.

**안드로이드에서 공지 이미지가 열리지 않던 문제**
원인은 학교 서버가 중간 인증서를 보내지 않는 것이었습니다. 서버 측 이미지 프록시로 우회하고, 도메인 화이트리스트와 리다이렉트 단계별 검사로 SSRF를 막았으며, 프록시 URL에는 HMAC 서명을 붙였습니다.

**동시 크롤링 충돌**
정기·초기·수동 크롤링이 겹치면 유니크 제약 위반으로 새 공지 배치 전체가 롤백됐습니다. 크롤링 진입점을 하나로 모으고 공용 락으로 직렬화했으며, 실패한 알림은 24시간 안에서 재전송하도록 했습니다.

**공지 상세 응답 지연**
캐시가 없으면 학교 사이트를 먼저 크롤링해서 약 1초가 걸렸습니다. DB에 저장된 내용을 즉시 응답하고 갱신은 백그라운드에서 URL당 10분에 한 번만 하도록 바꿨습니다.

`FastAPI` `SQLAlchemy (async)` `APScheduler` `PostgreSQL` `React Native` `Expo` `Docker` `GitHub Actions` `Oracle Cloud`
